# Phase A 機能要件 — 対戦ログMVP

> `10_business-plan.md` v0.2 の Phase A を開発要件に落としたもの。読者は開発セッション。
> ここでの「要件」は What まで。How（スキーマ・実装方式）は開発セッション側の裁量。
> 最終更新: 2026-07-31（事業計画セッション）

## 1. ゴール

**「誰かとプレイした記録が溜まっていく」体験を最小構成で成立させ、PMFを検証する。**

検証指標（`10_` §5）:

- North Star: 週次の対戦ログ作成数（相互確認済み比率を併記）
- PMF判定: 獲得ユーザーの4週後残存率 / ログ相互確認率 / 1ユーザーあたり累計ログ数の分布

## 2. スコープ

### In

1. 対戦ログの作成・相互確認（本要件の核。§3）
2. 個人アーカイブ（ログが溜まって見える画面。§4.2)
3. オンボーディング＝初回起動から最初のログまでの導線（§4.4）
4. フォロー中のプレイヤーのログが流れる小さなフィード（§4.3）
5. KPI計測の仕込み（§6）

### Out（やらない。理由つき）

| 項目 | 理由 |

| スイスドロー・大会進行管理 | Phase C。API連携優先の方針（`10_` §4） |
| バッジ・ポイント・プライズ | Phase B。ただしログ集計が素材になるため計測だけ仕込む |

## 3. コアオブジェクト: 対戦ログ

### 3.1 1件のログが持つ情報（要件レベル）

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| 対戦日時 | ✅ | 既定は「いま」。過去日も入力可 |
| 相手 | ✅ | ユーザータグ or 未登録相手のプレースホルダー（§3.3） |
| 勝敗 | ✅ | 勝ち/負け/引き分け。**スコア詳細やターン数は持たない**（入力摩擦を増やさない） |
| タイトル | ✅ | ポケカ/MTG/…の対応6タイトル |
| 使用デッキ名 | 任意 | フリーテキスト。デッキ機能とは切り離す |
| 場所・イベント | 任意 | チェックイン済みならイベント・店舗を**自動付与**（手入力させない） |
| ひとことメモ | 任意 | 短文1フィールドのみ |
| ソース | ✅（内部） | `manual` / `checkin連動` / `import`（外部取り込み用に最初から区別。§3.5） |

設計原則: **対戦後にテーブルの上で30秒以内に完了する入力量**を上限とする。項目追加の要望が出ても、この原則を超える場合は既定OFF・任意入力にする。

### 3.2 相互確認フロー

1. どちらか一方がログを作成し、相手をタグ（その場のQR/ID交換 or ユーザー検索）
2. 相手側に確認リクエストが届く（アプリ内通知）
3. 相手が承認 → **確認済みログ**として双方のアーカイブに載る
4. 未承認のまま → 作成者のアーカイブにのみ「未確認」として残る（相手側には出ない）

- 承認は勝敗込みのワンタップ。修正が必要なら差し戻しでなく「相手が自分視点で入力し直す」のが最短
- 拒否・無視されたログは作成者側で未確認のまま。相手のプロフィールには一切表示されない
- 虚偽・スパム対策: 同一相手への連続作成のレート制限、通報導線。チェックイン連動ログは「認証済み」表示で信頼度を区別（`10_` §9）

### 3.3 未登録の相手（重要・再会体験の入口）

「TCGアドバンスやってます？」→「やってない」の場合もログは作れる必要がある:

- 相手をプレースホルダー（表示名のみ）として記録できる
- 後日その人がアカウント登録した際に、**過去のプレースホルダーログを本人が引き取れる**（作成者からの紐づけ提案 → 本人承認で確認済み化）
- これが「あの時対戦してた人だ」という原体験（`10_` §1）の再現装置になるため、Phase Aから入れる

### 3.4 可視性

- 既定: 確認済みログは双方のプロフィールに公開（このサービスの根幹価値のため public を既定）
- ユーザー単位でアーカイブ全体を「フォロワーのみ/非公開」に切替可能
- 未確認ログは常に作成者にしか見えない

### 3.5 外部連携への布石（Phase Cの前提。今やるのはここまで）

- ログの `source` / 外部参照ID フィールドを最初から持つ
- ユーザーに**安定した公開ID**（表示名と別のimmutableなID）を持たせ、外部大会リザルトとの突合キーにできるようにする
- インポートAPI自体は作らない

### 3.6 データエクスポート

自分の全ログをエクスポートできる機能（形式は問わない。CSVで十分）。
「10年後も残る記録」への信頼の担保として Phase A から提供する（`10_` §9）。

## 4. 画面・体験

既存資産の再利用を前提とする: 戦績系モック `src/pages/BattlePages.tsx`、承認層は `useReactions` / `useFollows`、イベントは `useEvents`、チェックインは LiveEventDetail の実装を流用。

### 4.1 ログ作成フロー

- 起点は2つ: ①チェックイン中のイベント画面から（イベント・店舗が自動付与） ②ホームの「+ 対戦を記録」から（フリー対戦）
- 相手指定のためのQR/ID交換画面（自分のQRを見せる/読む）

### 4.2 個人アーカイブ（プロフィール統合）

- 日記ビュー: 時系列で「いつ・どこで・誰と・どのタイトル・勝敗」
- 集計サマリー: 累計対戦数、対戦相手数、タイトル別内訳、店舗別内訳（バッジ(Phase B)の素材と同じ集計）
- 相手名からその人のプロフィールへ遷移（フォロー・GGへの導線）

### 4.3 フィード（ホームの「準備中」を置き換え）

- フォロー中プレイヤーの確認済みログ＋チェックインが流れるだけの小さなフィード
- アルゴリズムなし・時系列のみ（`11_` パターン④を意図的に維持）

### 4.4 オンボーディング

- 初回起動〜最初のログ作成までを最重要導線として設計（協賛大会・店頭で入れた1,000人が最初の1件を作れるかがPMFの生命線。`10_` §6.3）
- 協賛大会・提携店経由の流入を識別できる仕込み（招待コード or 流入元パラメータ）を入れる

### 4.5 入口コンテンツ（🔶 スコープ判断をオーナーに提案）

`10_` §6.2 の「ログ以外のフック」。Phase A では**既存のイベント一覧・詳細を入口コンテンツと位置づけて磨く**（新規開発を増やさない）ことを推奨。
協賛大会のコンテンツ化（大会リザルトページ）は協賛案件が具体化した時点で Phase A.5 として追加判断。

## 5. 非機能・前提

- モバイルファースト430px、既存のデザイン原則（`design/`）に従う
- RLS: ログは当事者2名＋可視性設定に従う読み取り制御を必須とする
- 多言語対応・ネイティブアプリ化はやらない（PWA継続）

## 6. KPI計測の仕込み

- イベント計測: ログ作成 / 相互確認 / チェックイン / フォロー / GG、および流入元
- ベースライン取得（`10_` 次アクション2）: 現状のWAU・チェックイン実数を出すクエリを整備し、`00_current-state.md` に追記
- 週次で North Star（週次ログ作成数・相互確認率）を出せる状態にして Phase A リリースを迎える

## 7. 開発セッションへの申し送り・オープン論点

1. 相互確認の通知をアプリ内のみで始める判断の妥当性（未読に気づかず承認率が下がるなら、メール等の軽い補完を検討）
2. プレースホルダー相手の「引き取り」フローの詐称対策（他人のログを勝手に引き取れないよう、作成者の承認を挟む設計を推奨）
3. 既存 `BattlePages.tsx` モックと本要件の差分整理（モックは大会成績寄り。本要件は1対戦=1ログの日記型）
4. スキーマ・RLS設計はSupabase側の現状を踏まえて開発セッションが起案 → 大きな判断はこのファイルに追記して共有
