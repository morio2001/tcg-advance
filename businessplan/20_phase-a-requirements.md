**「誰かとプレイした記録が溜まっていく」体験を、ジャーニー①②（`12_` §2–3）が回る最小構成で成立させ、PMFを検証する。**

## 3. コアオブジェクト: 対戦ログ

### 3.1 1件のログが持つ情報（要件レベル）

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| 対戦日時 | ✅ | 既定は「いま」。過去日も入力可 |
| 相手 | ✅ | ユーザータグ or 未登録相手のプレースホルダー（§3.3） |
| 勝敗 | ✅ | 勝ち/負け/引き分け。スコア詳細やターン数は持たない |
| タイトル | ✅ | 対応6タイトル |
| 使用デッキ名 | 任意 | フリーテキスト |
| 画像 | 任意 | 1枚。公式デッキビルダーのスクショ等を想定。通報導線を用意 |
| 場所・イベント | 任意 | チェックイン済みならイベント・店舗を**自動付与**（手入力させない） |
| ひとことメモ | 任意 | 短文1フィールド |
| ソース | ✅（内部） | `manual` / `checkin連動` / `import`（外部取り込みに備え最初から区別） |

設計原則: **対戦後にテーブルの上で30秒以内に完了する入力量**を上限とする（画像添付は後からの編集でも可とする）。項目追加の要望が出ても、この原則を超える場合は既定OFF・任意にする。

### 3.2 相互確認フロー

1. どちらか一方がログを作成し、相手をタグ（その場のQR/ID交換 or ユーザー検索）
2. 相手側に確認リクエスト（アプリ内通知）
3. 承認 → **確認済みログ**として双方のアーカイブに載る
4. 未承認 → 作成者のアーカイブにのみ「未確認」として残る（相手側には出ない）

- 承認は勝敗込みのワンタップ。食い違いは「相手が自分視点で入力し直す」のが最短
- 虚偽・スパム対策: 同一相手への連続作成のレート制限、通報導線。チェックイン連動ログは「認証済み」表示で信頼度を区別

### 3.3 未登録の相手（再会体験の入口）

- 相手をプレースホルダー（表示名のみ）として記録できる
- 後日その人が登録した際に、過去のプレースホルダーログを**本人が引き取れる**（作成者の承認を挟む → 確認済み化）
- 原体験（`10_` §1）の再現装置。Phase Aから必須

### 3.4 可視性

- 既定: 確認済みログは双方のプロフィールに公開（サービスの根幹価値のため public 既定）
- ユーザー単位で「フォロワーのみ/非公開」に切替可
- 未確認ログは作成者にしか見えない

### 3.5 外部連携への布石（作るのはここまで）

- `source` / 外部参照IDフィールドを最初から持つ
- ユーザーに安定した公開ID（表示名と別・immutable）を持たせ、外部大会リザルトとの突合キーにする
- インポートAPI自体は作らない

### 3.6 データエクスポート

自分の全ログをCSV等でエクスポート可能に。「10年後も残る記録」への信頼の担保（`10_` §9）。

## 4. 画面・体験

既存資産の再利用前提: 戦績系モック `src/pages/BattlePages.tsx`、承認層 `useReactions` / `useFollows`、イベント `useEvents`、チェックインは LiveEventDetail を流用。

### 4.1 ログ作成フロー

- 起点2つ: ①チェックイン中のイベント画面から（イベント・店舗が自動付与） ②ホームの「+ 対戦を記録」（フリー対戦）
- 相手指定のQR/ID交換画面（自分のQRを見せる/読む）

### 4.2 個人アーカイブ（プロフィール統合）

- 日記ビュー: 時系列で「いつ・どこで・誰と・どのタイトル・勝敗」
- 集計サマリー: 累計対戦数、対戦相手数、タイトル別・店舗別内訳（バッジと同じ集計基盤）
- **月間サマリー**（何戦・何人・何勝）: ジャーニー②の月次振り返り。将来のプレミアムの原型
- 相手名からプロフィールへ遷移（フォロー・GG導線）

### 4.3 フィード（ホームの「準備中」を置き換え）

- フォロー中プレイヤーの確認済みログ＋チェックインが時系列で流れるだけ
- アルゴリズムなし（`11_` パターン④を意図的に維持）

### 4.4 オンボーディング＋流入計測

- 初回起動→**初ログ作成を1分以内**に完了できる導線（協賛大会の現場で成立することが生命線。`12_` §2 Day 0）
- 初ログで即バッジ付与（§5）
- 招待コード/流入元パラメータ: 協賛大会・提携店・紹介者のどれ経由かを計測。紹介した側に紹介バッジ

## 5. バッジ初期セット

- 付与条件はすべて**ログ・チェックイン集計から自動判定**（手動運用なし）
- 設計思想: 勝敗を称えない。**プレイ量・相手の多様性・通った場所**を称える（アンチオリパ = プレイすること自体が楽しい）
- 🔶 具体ラインナップはオーナー承認待ち。たたき台: 初ログ / 累計10・50・100戦 / 対戦相手10・30人 / 3タイトル制覇 / 同一店舗5・20回（常連） / 紹介バッジ
- 実装要件: バッジ定義をデータ駆動にし、追加が設定変更で済むこと（協賛大会の限定バッジを案件ごとに発行するため）

## 6. 集約イベントDB・店舗ページ・claim導線（GBPモデル）

- **アプリ側は「表示」のみ**: 店舗ページ（基本情報・イベント一覧・この店での公開活動=チェックイン/確認済みログ数）と、位置ベースの「近くのイベント」ビュー（既存 EventSearchPage の強化）
- イベント・店舗データは運営が投入（収集はスクレイピング＋人力キュレーションのオペレーション。アプリ要件外）。運営用の投入手段は最低限でよい（管理UIでも直接SQLでも可、開発セッション判断）
- 店舗ページに「**ビジネスオーナーですか？**」導線。Phase Aでは申請受付（フォーム/連絡先）まででよく、claim後の編集権付与は運用対応で開始
- カバー範囲はGTMエリア＋協賛大会商圏のみ。全国網羅はしない

## 7. KPI計測の仕込み

- イベント計測: ログ作成 / 相互確認 / チェックイン / フォロー / GG / バッジ付与 / 流入元
- ベースライン取得: 現状のWAU・チェックイン実数を出すクエリを整備し `00_current-state.md` に追記
- 週次で North Star（週次ログ作成数・相互確認率）を出せる状態でリリースを迎える

## 8. 非機能・前提

- モバイルファースト430px、既存デザイン原則（`design/`）に従う
- RLS: ログは当事者2名＋可視性設定に従う読み取り制御を必須
- ユーザー投稿画像（デッキスクショ）はストレージ容量とモデレーション（通報対応）を考慮
- 多言語・ネイティブ化はやらない（PWA継続）

## 9. 開発セッションへの申し送り・オープン論点

1. 相互確認の通知をアプリ内のみで始める判断の妥当性（承認率が低ければメール等の軽い補完を検討）
2. プレースホルダー引き取りの詐称対策（作成者承認を挟む設計を推奨）
3. 既存 `BattlePages.tsx` モックとの差分整理（モックは大会成績寄り、本要件は1対戦=1ログの日記型）
4. バッジ判定の実行方式（書き込み時トリガー/バッチ）は開発判断。ただし付与の遅延は「その場で称える」体験を損なうので最小に
5. スキーマ・RLS設計はSupabase現状を踏まえ開発セッションが起案 → 大きな判断は本ファイルに追記して共有
